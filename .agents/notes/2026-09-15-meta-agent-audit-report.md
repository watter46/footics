# 👑 メタエージェント設計監査レポート (2026-09-15)

## 1. 今回導入されたガード機構・探索パイプラインの批判的検証

### 機械的ガード (全体テスト・生ツール遮断)
* **妥当性**: ROI(トークン対効果)の観点では極めて優秀。`vitest run`の暴発による10kトークン超のコンテキスト汚染を確実に防ぐ。
* **副作用・過剰防衛 (Friction)**:
  * 現状の正規表現 `/^(rtk\s+)?(vitest(\s+run)?|pnpm\s+test.../` は局所的だが、ユーザーが明示的に「全テストを実行して」と指示した場合でもエージェントがDenyの壁にぶつかり混乱するリスクがある。
  * `find_by_name` / `grep_search` の完全遮断は、構造化JSONを期待するエージェントの基本動作を強制的にCLI文字列出力(`rtk find/grep`)へ捻じ曲げるため、初期の思考ステップで「Deny→再考」のオーバーヘッド（約200-500トークン）を毎度強いる。

### 4ステップ探索パイプライン
* **妥当性**: 未知の領域を探索する際の「型（パターン）」としては優秀であり、無駄なファイル全読み出しを防ぐ。
* **副作用・自己矛盾 (Complexity)**:
  * パイプラインの「絶対遵守」を強要すると、**既知のファイル（ユーザーがパスを指定した場合など）に対してすら、無駄な `tree` や `find` を実行する**という逆のトークン浪費（False Positive）を引き起こす。「未知領域の探索時のフォールバック」としての位置づけを明確にしない限り、ROIは悪化する。

## 2. Deny再試行 vs 透過的Proxy方式 の比較評価

**結論: `run_command` に関しては「透過的Proxy (overwrite)」が圧倒的に優位。生ツール遮断は「Deny」維持。**

* **論理的根拠 (ROI & DX)**:
  * AGYの `PreToolUse` フック仕様において、`overwrite` オブジェクトを返却することで引数(`CommandLine`)の透過的書き換えが可能。
  * 生の `vitest run <file>` を受け取った際、Denyしてエージェントに再入力を促すのではなく、バックグラウンドで `rtk vitest run <file>` に書き換えて実行させる。
  * 実行結果には「フックが引数を書き換えた」旨が通知されるため、**1ターンの浪費（トークン・時間）を削減しつつ、エージェントへの学習効果（教育）も維持できる**。
* **技術的限界 (Complexity)**:
  * `find_by_name` から `run_command` への「ツール自体の変更」は `overwrite` では不可能。したがって生ツールの直接呼び出しは現状通り Deny による誘導とするのが最もシンプルな最適解。
