# Test-Driven Development (テスト駆動開発スキル)

## 概要 (Overview)

新機能の実装やバグ修正を行う前に、必ず失敗するテストを書き、それが正しく失敗することを確認してから最小限の実装コードを書くためのスキルです。
Footics の「高品質な実装の担保」を満たすための核心的なアプローチです。

## 鉄の掟 (The Iron Law)

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
(失敗するテストを見る前に、プロダクションコードを1行も書いてはならない)
```

テストを書かずにコードを書き始めた場合、その変更を破棄してテストからやり直してください。例外はありません。

## Red-Green-Refactor サイクル

### 1. RED - 失敗するテストを書く
- 実装したい単一の振る舞いに対するテストを1つだけ作成します。
- 避けられない場合を除き、過度なモック化は避けて本物のオブジェクト/関数を検証します。
- テストを実行し、**期待通りに失敗すること（RED）** を必ず確認します。
  - コマンド: `bun run agent:check-worker <対象テストファイル>`
  - ※ 全体実行（無引数のテスト実行）はログ爆発防止のため禁止されています。
- 単なるインポートミスや構文エラーではなく、「期待した機能が未実装であること」が失敗理由であることをログで確認します。

### 2. GREEN - 最小限のコードを実装する
- テストを通過させるための「最もシンプルで最小限のコード」を書きます。
- この段階で余計な推測による抽象化や不要な機能追加（YAGNI違反）を行ってはなりません。
- テストを再実行し、**すべて通過すること（GREEN）** を確認します。
  - コマンド: `bun run agent:check-worker <対象ファイル群>`

### 3. REFACTOR - コードを整理する
- テストが GREEN になった後、重複排除、関数分割、リネームなどのリファクタリングを行います。
- リファクタリング中も、こまめにテストを実行して GREEN が維持されていることを確認します。

## 良いテストの鉄則 (Test Quality Principles)

1. **壊れる箇所を命名する (Name the Break)**:
   - テスト名は「プロダクションコードのどの振る舞いが壊れたときに失敗するか」を明確に示します。
2. **本物を検証する (Exercise the Real Thing)**:
   - 外部I/Oや極端に遅い処理を除き、可能な限り実オブジェクト・実関数をそのまま検証します。
3. **手動導出リテラルの利用 (Hand-derived Literals)**:
   - 期待値の計算にプロダクションコードのヘルパーを流用せず、ハードコードされたリテラル値（例: `expect(result).toBe("tag:urgent")`）で検証します。
4. **変更検知器にしない (No Change Detectors)**:
   - 定数値やUIの文言など、意図的な仕様変更で壊れるだけのテストは書かず、振る舞い（契約）を検証します。

## Phase 内完結の原則
各 Phase のスコープ内で TDD を完全に完結させ、次 Phase の Worker または Reviewer にクリーンな状態でハンドオフします。

## 完了前チェックリスト

- [ ] 実装したすべての新機能・振る舞いに対するテストが存在する
- [ ] 実装前に、各テストが期待通りの理由で失敗（RED）したことを確認した
- [ ] テストを通過させるための最小限のコードのみを実装した
- [ ] `bun run agent:check-worker <対象ファイル群>` を実行し exit code 0 である
