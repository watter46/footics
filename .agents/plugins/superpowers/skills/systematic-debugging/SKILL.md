# Systematic Debugging (体系的デバッグスキル)

## 概要 (Overview)

バグ、テスト失敗、ビルドエラー、予期しない動作に直面した際、推測による対症療法を禁じ、根本原因（Root Cause）を体系的に特定・解決するためのスキルです。

## 鉄の掟 (The Iron Law)

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
(根本原因の調査完了前に、いかなる修正コードも提案・実装してはならない)
```

Phase 1（根本原因の調査）を完了しないまま、コードの修正・パッチ当てを行ってはなりません。

## デバッグの4フェーズ (The Four Phases)

### Phase 1: 根本原因の調査 (Root Cause Investigation)
修正コードに触れる前に、以下を完全に実施してください：

1. **エラーメッセージの完全な精読**:
   - スタックトレース、行番号、ファイルパス、エラーコードを読み飛ばさない。
2. **再現の確定**:
   - 確実に再現する最小の手順・テストケースを特定する。
3. **直近の変更の差分確認**:
   - `rtk git diff` や `rtk git log -n 5` で何が変更されたかを確認する。
4. **多層システムにおけるエビデンス収集**:
   - どこでデータが壊れたか（入力・出力境界）を特定する。
5. **データフローの逆追跡 (Backward Tracing)**:
   - 不正な値がどこで生成され、誰から渡されたかを呼び出し元へ遡って特定する。症状が出た場所ではなく、原因の発生源で修正する。

### Phase 2: パターン分析 (Pattern Analysis)
1. **正常に動いている既存コードの調査**:
   - 同一リポジトリ内で正常に動作している類似機能を見つける。
2. **差異のリストアップ**:
   - 動いているコードと壊れているコードの差分を洗い出す。
3. **前提条件と依存関係の確認**:
   - 型定義、環境変数、設定値の不一致を確認する。

### Phase 3: 単一仮説と最小検証 (Hypothesis & Testing)
1. **明確な仮説の立案**:
   - 「原因は A であり、理由は B である」と言語化する。
2. **最小限の検証**:
   - 仮説を検証するための最小の1箇所のみを変更・確認する（一度に複数の修正を入れない）。
3. **仮説が外れた場合**:
   - 変更を一度元に戻し、新たな仮説を立て直す（失敗したパッチの上に修正を重ねない）。

### Phase 4: 実装と根本修正 (Implementation)
1. **失敗するテスト（再現テスト）の作成**:
   - `test-driven-development` スキルに従い、バグを再現するテストコードを先に書く（RED）。
2. **最小限の根本修正の実装**:
   - 根本原因となった箇所を修正し、テストが通過することを確認する（GREEN）。
3. **波及確認とリファクタリング**:
   - 関連するスコープのテスト（`pnpm run agent:check-worker <ファイル>`）を実行し、他への影響がないことを検証する。
