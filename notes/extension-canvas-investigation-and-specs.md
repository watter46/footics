## 1. 目視検証結果・原因調査の突合ログ

### #1-1: 別タブ遷移時のパフォーマンス・初期ロード速度
- **現象**: 別タブ（`canvas.html`）へ遷移した際の初期表示速度・最適化懸念。
- **原因・コード実態**:
  - `extension/features/canvas/components/QuickTacticalCanvas.tsx` において、`id` パラメータ取得後に IndexedDB（`screenshot-db`）からフルサイズ Base64 Data URL を取得。
  - その後 `useStandaloneCanvasSession` で Zustand ストアを初期化し、さらに `UnifiedCanvas` 側で Konva の画像オブジェクト生成（`new Image()`）を行うため、**「DB取得待ち → React再レンダリング → HTML Imageデコード」の直列ウォーターフォール**が発生している。
  - 初期レンダリング時に Footics 本体の全モジュール（不要なピッチ線コンポーネント、ビデオエクスポート、アニメーション等）がまとめてロードされている点も初期表示速度に影響。

### #1-2: 画像周りの黒マージン & 境界線の全画面化 / リロード時の一瞬の2Dピッチ・マーカー表示
- **現象**:
  1. スクリーンショットがフルスクリーンで撮れるが、キャンバス貼り付け時に画像の周囲に黒いマージンがあり、境界線を全画面にすると黒い部分が入り込んでしまう。デフォルトで画像を画面いっぱいにし、境界線もデフォルトで画面いっぱいにしたい。
  2. リロードした際、2Dピッチや2Dマーカー、ツールが一瞬表示され、その上にスクショが被さるように見える（副作用・チラつき）。
- **原因・コード実態**:
  1. **黒マージンの原因**:
     - `src/features/tactical-unified/objects/pitch/components/pitch-background.tsx`（79〜82行）および `pitch-background-dom.tsx`（115〜116行）で、**周囲にポインタハンドル用の余白として 2%（全体4%）のマージン（`x: width * 0.02, width: width * 0.96`）がハードコード**されている。
     - さらに `use-standalone-canvas-session.ts`（50行）で初期境界線として `DEFAULT_BOUNDARY_BOX_SCREENSHOT`（`x: 2, y: 2, width: 96, height: 96`）が適用されているため、境界線を全画面（100%）に広げると外側2%の黒地（`#020617`）が写り込む。
  2. **リロード時のチラつき（Flicker）の原因**:
     - `tactical-unified-store.ts` の**初期状態（State初期値）**が「2Dピッチ背景（`backgroundType: 'pitch'`）」かつ「デフォルト選手11人配置（2Dマーカー）」で定義されている。
     - `QuickTacticalCanvas` マウント直後はストアのデフォルト値（Footics 本体の2Dサッカー盤状態）で初回復帰レンダリングが走り、その直後の `useEffect` 内で非同期に IndexedDB からスクショを取得して `resetProject()` → `backgroundType: 'image'` かつ選手ベンチ退避の更新を行うため、**数フレーム間、2Dピッチと2D選手が画面にチラついてからスクショで覆い隠される**副作用が発生している。

### #1-3: デフォルト全画面 & ウィンドウリサイズ（ハーフ化）での比率崩れ
- **現象**:
  - 切り替えの実装はできているがデフォルトを全画面にしたい。
  - ブラウザをモニター半分のハーフサイズにリサイズすると画像の ratio が変更されてしまう。全画面で使う前提にするか、キャンバスの大きさに合わせて ratio を変更しないようにしたい。
- **原因・コード実態**:
  - `src/features/tactical-unified/objects/canvas/components/unified-canvas.tsx`（86〜89行）および `calculatePitchRect`（`pitch-geometry.ts`）の実装：
    - ステージの表示枠（`stageSize` = コンテナ幅・高さ）に対して、現在の `aspectRatio` を維持した最大の矩形を計算し中央配置している。
    - ウィンドウをハーフサイズにリサイズするとコンテナ幅が激減し、ステージ自体の縦横比や BoundaryBox の正規化座標（0〜100%）のピクセル変換率が変動し、画像描画比率や枠線が引っ張られてしまう。
  - **再設計での検討方針**: キャンバス全体の論理解像度（内部仮想キャンバス）を固定し、CSS/Konvaの表示スケーリング（`object-fit: contain` 相当のレターボックス）で常に元アスペクト比を保持する構造にする。

### #1-4: X（Twitter）共有機能の仕様確定
- **仕様確定内容**:
  - **「Xを開いて自動画像コピー ＋ 空文（文章なし）」**
- **コード実態 & 技術的制約**:
  - `QuickCanvasTopBar.tsx` / `QuickTacticalCanvas.tsx`（124〜128行）の `text=` パラメータを空にし、定型文を一切載せない。
  - X（Twitter）の Web インテント URL（`https://twitter.com/intent/tweet`）はセキュリティ仕様上、URLパラメータ経由でのローカル画像バイナリ直接添付をサポートしていない。
  - そのため、「X共有ボタン押下時にクリップボードへ画像PNGを自動コピー → 空文のX投稿画面を新規タブで起動 → ユーザーが `Ctrl + V` で画像を貼り付けられる」フローを確定仕様とする。

### #2-a: Figma風・英語ラベルUI

## 2. 根本課題と再設計（アーキテクチャ分離）の必要性

現在発生している副作用（チラつき、黒マージン、不要な依存のロード遅延）は、**「Footics 本体の戦術盤前提の巨大な Store・コンポーネント」を Extension にそのまま流用していること**が根本原因。

### 再設計方針: 小さく作って組み合わせる (Composable Architecture)
1. **Pure Annotation Core（軽量描画コア）の分離**:
   - サッカー特有のドメイン（ピッチ線、選手11人、ボール、スライド）を含まない、画像背景と Konva 描画（線・矢印・ゾーン・リング・テキスト）に特化した疎結合コア。
2. **Extension 独立初期化**:
   - 初期化時から「画像背景」「選手0」でマウントし、本体用ストアのデフォルト値を踏ませない（チラつきゼロ）。
3. **ゼロマージン描画**:
   - 画像表示および BoundaryBox の初期値を 100% 全画面・マージン0 とする。
4. **論理座標・アスペクト比固定**:
   - ウィンドウサイズがハーフになっても画像比率が崩れないコンテナスケーリング。
