# Regista GM 実務原則 (Practices)

## P1: コンテキスト最小化の原則
- タスクをサブエージェントに委譲する際、プロジェクト全体のコンテキストではなく、
  関連する最小単位のディレクトリ・KI・型定義のみを渡す
- 不要な情報によるハルシネーションと文脈肥大化を防止

## P2: Contract-First 分解の原則
- 実装に先立ち、必ず型定義(TypeScript)・Zodスキーマ・インターフェースを確定させる
- 並行作業の衝突を防ぎ、各エージェントが独立して実装可能にする

## P3: 決定論的検証優先の原則
- LLMによるSemantic検証の前に、必ずツールベースの決定的検証を通す
- (1) `rtk biome check` → (2) `rtk tsc --noEmit` → (3) `rtk vitest run <対象パス>` → (4) Semantic Review
- **検証スコープの限定義務**: テストや型チェックはプロジェクト全体を無差別に実行せず、必ず変更モジュール・影響範囲に絞って実行する（例: `rtk vitest run <影響対象パス>`）

## P4: エスカレーション階梯の原則
- 3回連続で同一エラーが解消しない場合、仕様側の問題を疑う
- Level 1: 自動リトライ → Level 2: GM介入・仕様緩和 → Level 3: オーナーへ確認

## P5: Knowledge Item 駆動の原則
- タスク着手前に必ず .agents/knowledge/ の関連KIを確認させる
- タスク完了後にKIを自律更新させ、組織の知識を蓄積する

## P6: 境界明確化の原則
- パッケージ間（src/, extension/, video-canvas/）の直接参照を禁止
- 型定義のみ共有可能、循環参照は絶対に作らない

## P7: インクリメンタル変更の原則
- 一度に一つの変更のみ行う（機能追加とリファクタリングの同時実施を禁止）
- 変更後は古い参照が残っていないかgrepで確認

## P8: 指示書品質の原則 (GM特有)
- サブエージェントへの指示は「役割」「具体的タスク」「前提条件」「納品基準」の4要素を必須とする
- 丸投げ禁止、曖昧な指示は出さない
- **パフォーマンス制約の明示**: UI/Canvas/アニメーション/D&D を扱うタスクの場合、必ず「過渡状態の管理方法（State更新禁止）」「Layer分離」「セレクター細粒度化」等のパフォーマンス必須要件を指示書に含める

## P9: デプロイメント自動化の原則
- src/変更後は rtk pnpm run deploy を実行
- extension/video-canvas/ 変更後は rtk pnpm run build を実行
- ビルド/デプロイ失敗時は即座にエラー原因を特定・報告

## P10: 責務の重複排除の原則
- 複数のエージェントが同じファイル・モジュールを同時に編集する状況を避ける
- 同一ドメインのタスクは直列化する
